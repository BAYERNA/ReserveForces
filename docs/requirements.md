# 요구사항 정의서 (Requirements Specification)

> 2026년 「예비전력분야 혁신 아이디어」 공모전 — 혁신 서비스 개발 분야
> **예비군 동원소집 통합 관제 시스템**

| 문서버전 | v1.0 | 작성일 | 2026-09-02 |
|---|---|---|---|
| 작성자 | BAYERNA (개인 참가) | 문서상태 | 초안 |

## 1. 문서 개요

### 1-1. 목적
본 문서는 「2026년 예비전력분야 혁신 아이디어 공모전」 혁신 서비스 개발 분야 제출을 위해 기획된 '예비군 동원소집 통합 관제 시스템'의 기능·비기능 요구사항을 정의하여, 설계 및 개발의 기준으로 삼기 위해 작성되었다.

### 1-2. 적용 범위
1인 개발 및 약 8주(접수~2차 발표심사)의 개발 기간을 전제로, 시연 가능한 MVP(핵심 관제 대시보드 + 규정 기반 자동판정) 범위를 우선 정의하고, 확장 모듈(챗봇, 신원확인)은 향후 확장 요구사항으로 별도 구분한다.

### 1-3. 용어 정의

| 용어 | 정의 |
|---|---|
| 소집대상자 | 동원훈련 소집 통지를 받은 예비군 개인 |
| 지연입소 | 지정된 입영시간을 초과하여 입영하는 것. 규정상 1시간 이내는 허용 처리 |
| 조기퇴소 | 거주지가 소집부대로부터 100km 이상인 경우 등 사유로 조기 퇴소가 허용되는 것 |
| 룰엔진 | 지연입소·조기퇴소 판정 규정을 코드화하여 입력값에 따라 자동으로 결과를 산출하는 판정 로직 |
| 시나리오 데이터 | 네트워크 제한 환경에서의 시연을 위해 미리 준비한 가상 소집대상자·입영 데이터셋 |

## 2. 이해관계자 및 사용자 역할

| 역할 | 사용자 | 주요 필요 |
|---|---|---|
| 관리자 | 부대 동원 담당자 | 소집 현황 실시간 파악, 지연/조기퇴소 처리 확인, 전체 진행률 관리 |
| 일반 사용자 | 소집대상 예비군 | 본인 소집통지 확인, 입영 부대·훈련장 정보 조회, 본인 판정 결과 확인 |

## 3. 기능 요구사항

※ 우선순위 기준(MoSCoW): Must=1차 MVP 필수, Should=여유 시 포함, Could=확장 로드맵(2차 시연 이후)

| ID | 요구사항명 | 상세 설명 | 우선순위 | 대상 역할 |
|---|---|---|---|---|
| FR-01 | 로그인 및 권한 분리(RBAC) | 관리자/일반 사용자 계정으로 로그인하며, 역할에 따라 접근 가능한 화면과 기능이 구분된다. | Must | 공통 |
| FR-02 | 소집대상자 현황 조회 | 관리자가 소집부대·기간별 소집대상자 명단과 현재 상태(소집 전/입영/지연/조기퇴소 등)를 조회한다. | Must | 관리자 |
| FR-03 | 입영 진행률 대시보드 | 전체 소집대상자 대비 입영 완료 인원 비율, 상태별 인원수를 실시간(또는 시나리오 갱신 시점)으로 시각화한다. | Must | 관리자 |
| FR-04 | 지연입소 자동판정 | 입영시각 입력값을 기준으로 지정 입영시간과 비교하여 1시간 이내 여부를 규정에 따라 자동 판정한다. | Must | 관리자 |
| FR-05 | 조기퇴소 자동판정 | 소집대상자 거주지-소집부대 간 거리값을 기준으로 100km 이상 여부를 규정에 따라 자동 판정한다. | Must | 관리자 |
| FR-06 | 판정 결과 수동 보정 | 자동판정 결과에 대해 관리자가 예외 사유를 기재하고 결과를 수동으로 보정할 수 있다. | Should | 관리자 |
| FR-07 | 소집통지 확인(개인) | 일반 사용자가 본인에게 발송된 소집통지(일시·장소·부대)를 조회한다. | Must | 일반 사용자 |
| FR-08 | 입영 부대·훈련장 정보 조회 | 일반 사용자가 입영할 부대·훈련장의 위치, 연락처 등 기본 정보를 조회한다. | Should | 일반 사용자 |
| FR-09 | 본인 판정 결과 확인 | 일반 사용자가 본인의 지연입소·조기퇴소 판정 결과를 조회한다. | Should | 일반 사용자 |
| FR-10 | 처리 이력 로그 | 판정·보정 처리 내역을 시각·처리자와 함께 이력으로 기록하고 조회할 수 있다. | Should | 관리자 |
| FR-11 | 시나리오 데이터 시연 모드 | 사전 적재된 가상 데이터셋으로 전체 기능을 네트워크 연결 없이 시연할 수 있는 모드를 제공한다. | Must | 공통 |
| FR-12 | 소집·훈련 안내 챗봇(확장) | 지연입소 기준, 훈련 일정 등 반복 질의에 대해 사전 정의된 응답을 제공한다. | Could | 일반 사용자 |
| FR-13 | 현장 신원확인 모듈(확장) | 영상 인식 기반으로 입영 인원의 신원을 확인하고 입영 기록에 자동 반영한다. | Could | 관리자 |

## 4. 비기능 요구사항

| 분류 | 항목 | 요구 내용 |
|---|---|---|
| 가용성 | 오프라인 시연 | 외부 API·인터넷 연결 없이 핵심 기능(FR-02~05, 07~09, 11)이 정상 동작해야 한다. (2차 발표심사 규정 대응) |
| 보안 | 권한 분리 | 관리자/일반 사용자 권한을 서버 측에서 검증하며, 타인의 개인 소집정보에 접근할 수 없어야 한다. |
| 보안 | 개인정보 보호 | 소집대상자의 이름·연락처 등은 시연용 가상 데이터로 대체하며, 실제 개인정보는 저장하지 않는다. |
| 사용성 | 반응형 웹 | 별도 앱 설치 없이 PC·모바일 브라우저에서 동일 서비스에 접근할 수 있어야 한다. |
| 성능 | 응답 속도 | 대시보드 조회 및 판정 처리는 시연 환경(로컬 구동) 기준 2초 이내 응답을 목표로 한다. |
| 확장성 | 모듈 구조 | 챗봇, 신원확인 등 확장 모듈이 기존 도메인 로직 변경 없이 부가 기능으로 연결될 수 있는 구조여야 한다. |
| 이식성 | 타 부대 적용 | 소집부대·훈련장 정보를 데이터로 관리하여 코드 수정 없이 다른 부대에도 적용 가능해야 한다. |

## 6. 데이터 요구사항

| 엔티티 | 주요 속성 | 비고 |
|---|---|---|
| 사용자계정 | 계정ID, 역할(관리자/일반), 소속부대 | FR-01 연계 |
| 소집대상자 | 성명(가상), 소집부대, 거주지 거리값, 상태 | 시연용 가상 데이터 |
| 소집부대/훈련장 | 부대명, 위치, 지정 입영시각, 연락처 | 타 부대 확장 대비 데이터화 |
| 입영기록 | 대상자ID, 실제 입영시각, 상태 | FR-02, FR-03 연계 |
| 판정결과 | 대상자ID, 판정유형(지연/조기), 자동/수동 여부, 사유 | FR-04~06 연계 |
| 처리이력 | 처리자, 처리시각, 처리내용 | FR-10 연계 |

※ 모든 인적 데이터는 실제 개인정보가 아닌 시연용 가상 데이터로 구성한다.

## 7. 제약사항 및 가정

- 개발 기간: 접수(~10/30) 이후 1차 심사 결과(11/13)까지 약 8주 내 MVP(Must 우선순위) 완성을 목표로 한다.
- 2차 발표심사는 네트워크가 제한되는 환경에서 진행될 수 있으므로, 모든 Must 요구사항은 오프라인 동작을 전제로 설계한다.
- 1인 개발을 전제로 하며, Could 우선순위 항목(FR-12, FR-13)은 일정에 여유가 있을 경우에만 착수한다.
- 실제 국방동원정보체계·예비군 홈페이지와의 시스템 연동은 범위에서 제외하며, 자체 데이터베이스 기반으로 독립 구동한다.

## 8. 요구사항 우선순위 요약

| 우선순위 | 포함 요구사항 | 개발 단계 |
|---|---|---|
| Must | FR-01, 02, 03, 04, 05, 07, 11 | 1차 MVP — 접수~1차 심사 이전 완료 |
| Should | FR-06, 08, 09, 10 | 2차 발표심사 전 여유 시 보강 |
| Could | FR-12, FR-13 | 향후 확장 로드맵(발표자료에 계획으로 제시) |

> 본 저장소의 현재 구현은 Must + Should(FR-01~11)를 MVP 범위로 포함한다.
